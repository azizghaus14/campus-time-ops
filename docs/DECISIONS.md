## D-01 Stack
We use Python + FastAPI for REST, FastMCP for MCP, OR-Tools CP-SAT for the solver, and Next.js 16 with Tailwind 4 and Recharts 3 for the dashboard. Everything runs on Cloud Run in asia-southeast1, as specified. One backend process serves both `/api` (REST) and `/mcp` (MCP over streamable HTTP), and both call the same service functions.

## D-02 Agent platform: Gemini Enterprise first, ADK fallback ready (VERIFY in the tenant)
- **Primary path:** Gemini Enterprise chat agents (`agents/replan`, `agents/slot_finder`) connect to the backend through the third-party **MCP server** connector, at `https://<api>/mcp` over streamable HTTP with a bearer token. The configs are in `agents/*/config.yaml` and the instructions in `agents/*/instructions.md`.
- **Fallback:** `agents/adk_app/agent.py` builds the same two agents with **Google ADK**, as a router plus sub-agents, consuming the **same** MCP server. `approve_proposal` and `execute_proposal` sit in a separate toolset with `require_confirmation=True`, so ADK asks the user before calling them, and the server enforces approval as well. We tested this locally: ADK discovers 20 tools from the running MCP server. It has not been tested against Vertex AI, because the build environment had no GCP credentials.
- **Status:** the build environment had no access to the hackathon tenant. Before the demo, the team must check whether their Gemini Enterprise edition can add a custom MCP server as a data connector or tool. If it can, use the primary path. If not, deploy `agents/adk_app` to Vertex AI Agent Engine (`adk deploy agent_engine`) or run `adk web`. **Record which path was used here: ____.**

## D-03 MCP SDK pinned to v1 (`mcp>=1.9,<2`)
`pip install mcp` now installs 2.x, where FastMCP has been renamed `MCPServer` and other APIs have changed. The spec asks for FastMCP, and the v1 API is the one documented by Google, ADK and the MCP Inspector, so we pinned v1 (1.30.0). DNS-rebinding protection is turned off because a bearer token protects the endpoint and Cloud Run hostnames vary.

## D-06 Shuttle rule
The rule uses the **LRT Bukit Jalil** route, which serves all students. Its last *regular* departure is 19:15; the 20:45 and 21:45 trips are marked "limited space". A physical make-up class must therefore end by 19:00 (R-SHUTTLE). The PDF publishes no Saturday service, so there is no physical make-up class on Saturday unless the rule is relaxed. `SHUTTLE_INCLUDE_LIMITED=true` counts the limited trips.

## D-07 Mock capacities and headcount
Room capacities follow the heuristics in the brief, seeded per room name. Group sizes are seeded at 15–60 per (intake, grouping). Combined lectures would then exceed the room they already fit in today, so a session's **headcount is capped at a seeded 60–95% of its current room's capacity**. This keeps every original assignment feasible and the numbers stable.

## D-08 Room-type rule
Classrooms move to classrooms, labs to labs, and auditoriums to auditoriums or large classrooms. A specialist room (studio, workshop, geology lab, iMac suite and so on) can only be replaced by the **same room** (R-ROOM-TYPE).

## D-09 Term calendar for the attendance forecast
The feed covers only about 3 weeks. For each intake group:
- **Inside the window,** the forecast uses the real sessions, after any executed re-plans.
- **Before the window,** it repeats each (module, weekday, start) pattern weekly, back to the module start date in the `CLASS_CODE` suffix.
- **After the window,** it repeats them weekly up to `TERM_END` (default 2026-12-18, the last teaching day before the Year End Break), skipping holidays.

Attendance is computed **per module**, as HB §2.2 requires. `max_more_absences` is exact rational arithmetic, and a test compares it against a brute-force hand calculation.

## D-10 Solver design
- **Pre-filtering:** only candidates that are feasible against the fixed timetable become variables (day × standard-grid start or the original start × room). There are 15-minute ticks between 08:30 and 21:00.
- **Pairwise rules:** constraints between moved sessions are `AtMostOne` over every room, lecturer and group time point.
- **Warm start:** a greedy solution gives CP-SAT its hint, and it is also the fallback if CP-SAT returns nothing.
- **Decomposition:** the problem is split by school when it has more than 900 sessions or when the single model fails. It is also forced in a test.
- **Clash check:** an independent checker runs after every solve and also checks approver edits.
- **Determinism:** small solves use a single worker with a fixed seed, which makes them deterministic (tested). Bulk solves use 8 workers.
- **Speed:** a whole-campus holiday (about 600 sessions) solves to OPTIMAL in about 2.5 s.

## D-11 Notice period exception
Changing only the room, or swapping the lecturer, at the original time needs no 24-hour notice, because the students' time commitment does not change. This exception is documented in R-NOTICE.

## D-12 State and actions
- **State:** Firestore in the cloud (`STORE_BACKEND=firestore`). Locally, JSON files sit behind the same interface.
- **Workspace actions:** `WORKSPACE_MODE=google` calls the Calendar API, the Gmail API (`drafts.create` only) and the Docs API, using the OAuth token of a **demo** account. `local` mode writes real `.ics`, `.eml` and markdown files into `data/outbox`. The offline demo uses local mode.
- **Guard:** every recipient must be on `WORKSPACE_DEMO_DOMAIN`.
- **Overlay:** executed moves become an in-memory overlay that is replayed at startup, so the Cloud Run backend runs as a single instance.

## D-14 Scope trim v2 (applied 2026-11-12, from `TRIM_PROMPT.md`, confirmed by the team)
**Why:** the product has to tell one story: *APU's live timetable, re-planned by agents, with a human approving every step.* Features that weren't about time, rooms and who is where diluted the pitch, relied on unverifiable assumptions, or turned into a generic chatbot.

**Removed:**
- passport reading, MRZ parsing and check-digit validation, including the specimen images
- visa and student-pass renewal planning, with the pass and passport expiry fields
- the escalation ladder
- the separate scheduled workflow agent with its 09:00 digest
- the Ops Q&A chatbot
- energy, kWh and RM estimates
- `send_drafts`: the system only ever creates Gmail drafts
- mock exam data
- all international-student and immigration framing

**Shrunk:**
- Visa Guardian became **Attendance Risk**: a read-only feature for all students, made of `get_attendance`, `attendance_forecast` and `attendance_risk_list`, with one dashboard page. The Replan agent answers "how many more classes can I miss?".
- Synthetic students now carry only `id, name, intake, grouping, attendance_records`.
- Rooms & Energy became **Rooms**.

**Added:** the **substitute-lecturer finder** (`find_substitutes`). For a `LECTURER_UNAVAILABLE` disruption, Replan tries a substitute first, keeping the same time and room so no student is affected. A substitute must teach the same module (same MODID section, or the same module base or name), be free, and stay within 3 sessions that day. The solver reschedules only the rest. Each move is typed SUBSTITUTE, RESCHEDULE or ONLINE, and unresolved sessions are typed UNRESOLVED. On execution the substitute is asked to confirm by Gmail draft, and the groups get a short notice.

"Same programme prefix" in the ranking is applied as a same-school bonus *among lecturers who already teach the module*. That way a substitute always genuinely teaches the module, as the acceptance test requires.

**Scope check:** `scripts/check_scope.sh` searches the product for the removed terms and excludes this note and the two original prompt files (`BUILD_PROMPT.md`, `TRIM_PROMPT.md`), which are kept as the project brief.

## D-15 Attendance risk scoring
A student is "at risk" when the score is 30 or more. Points come from:
- cannot reach the threshold in a module: +100
- a slipping module (below 90%) with 0, 1 or 2 absences left: +50, +35 or +20
- currently below the threshold: +40
- within 3 points of the threshold: +15
- projected below the threshold at term end: +25
- 3 or more consecutive absences: +20
- a declining trend: +10

Plain arithmetic is not counted as risk. For example, a student at 100% with 3 sessions left "can miss 2" but is not at risk. About 43% of the synthetic students are flagged, because the generator deliberately gives about 40% of them declining, sudden-drop or at-risk profiles.
